# Что собираем?

Онлайн-сборка пазлов — одному или с друзьями. Идея зафиксирована
2026-08-23. Соло-ядро (без входа — встроенные пазлы без сохранения, со
входом — те же пазлы с прогрессом в SQLite) реализовано; дизайн
подключён (вещество бор, повадка искр interlock). Комнаты с realtime-
сборкой через WebSocket реализованы (см. «Комната» и «Стол» ниже).
Свои фото на пазл реализованы (см. «Свои фото» ниже). Загрузка через
Admin — ещё нет, отдельной задачей. Здесь — что решено и что ещё
предстоит продумать.

Название по конвенции из `Design/services.md` — вопрос, который
спрашивают вслух, тот же приём, что у «Что смотрим?».

Домен: `puzzle.burninghouse.ru`. Аккаунты — общие, через
[BurningHouse Auth](../Auth/INTEGRATION.md); client_id для регистрации
клиента — `puzzle`, по образцу остальных сервисов.

## Идея в двух режимах

**Без входа** — доступны только пазлы из встроенного набора сервиса
(картинки грузит админ через Admin, см. ниже). Собрал и ушёл, без
сохранения между сессиями — как «Пораскинем мозгами?».

**После входа** (SSO через [`Auth`](../Auth/INTEGRATION.md), как у
остальных сервисов) — можно:
- создавать комнаты и собирать пазл с друзьями;
- загружать свои фото и собирать их в комнате в 4 уровнях сложности
  (реализовано, см. «Свои фото» ниже) — только в комнатах, соло-режим
  своих фото не показывает;
- прогресс сохраняется между сессиями.

## Детали пазла

Не прямоугольная сетка — детали фигурные, как в настоящих пазлах:
выступы и пазы, совпадающие у соседних деталей. Реализовано в
`assets/puzzle-shapes.js` — SVG `<path>` на деталь, форма детерминирована
по seed пазла, общее ребро у соседей строится из одних чисел в
противоположном порядке обхода, поэтому контуры совпадают без
дополнительной синхронизации.

## Комната

Реализовано: создание комнаты, список участников (роли `owner` —
создатель, остальные `member`), история прошлых сборок, библиотека
пазлов внутри комнаты (тот же список, что и в соло). Принятые решения:

- **Вход только по ссылке-приглашению** (`#/rooms/join/:joinCode`) —
  пикер друзей через Auth API сознательно не сделан в этом заходе
  (кросс-доменный CORS с `auth.burninghouse.ru` не проверен, лишняя
  внешняя зависимость).
- **Начать сборку может любой участник**, не только owner — это
  компания друзей, а не иерархия. Роль в `room_members` хранится, но
  сейчас ничем не гейтится, кроме факта членства в комнате.
- **Один активный сеанс сборки на комнату** — гарантируется частичным
  уникальным индексом в SQLite (`room_sessions`, `WHERE completed_at
  IS NULL`), повторный старт при уже активном сеансе отбивается 409.
- Кнопка «за стол» переводит из комнаты на отдельный экран стола —
  там происходит сама сборка.

## Стол

- Детали двигаются drag-and-drop, тот же код, что и в соло
  (`scatterLayout`, `createPieceEl`, фигурные детали).
- Масштабирование (zoom) и панорама — пазл на много деталей не
  поместится на экране в масштабе 1:1; камера при этом локальная у
  каждого клиента, не синхронизируется.
- **Совместная сборка в реальном времени — через WebSocket**
  (`Puzzle/ws-server.js`, голая реализация RFC 6455 поверх
  `http.Server`'s `'upgrade'`, без внешних зависимостей — в Node 22
  своего серверного WebSocket нет). WS-эндпоинт привязан к сеансу
  сборки, а не к комнате: `/ws/rooms/:roomId/sessions/:sessionId`.
  Аутентификация — токен как query-параметр (`?token=…`, браузерный
  `WebSocket` не даёт задавать заголовки), проверяется тем же
  `auth.verify()`, что и обычные API-запросы.
- Раскладка деталей не дублируется на сервере: `room_sessions.pieces`
  стартует как `NULL`, первый клиент, увидевший это в `sync`, считает
  раскладку локально и присылает `init` — сервер принимает первый
  валидный `init` как каноническую раскладку и рассылает всем; гонка
  двух одновременно открывших стол клиентов самоисцеляется.
  Позиции деталей и прогресс сборки хранятся на комнату целиком (общий
  прогресс, не свой на игрока) — персист в SQLite дебаунсится (~1.5с
  активности), финальный снап и уход последнего участника со стола
  флашатся немедленно.

## Свои фото

Вошедший пользователь может загрузить своё фото и собрать из него
пазл — **только в комнатах**. Соло-библиотека (`#/`) своих фото не
показывает и не грузит форму загрузки вовсе; прямой переход на
`#/table/:id` для чужого/своего кастомного пазла блокируется явным
сообщением («пазлы из своих фото собираются только в комнатах»)
вместо тихой попытки собрать стол. Публикация своих фото в общую
библиотеку — отдельная будущая задача (см. «Открытые вопросы» ниже).
Принятые решения:

- **Один аплоад — сразу 4 варианта сложности**: 12 (Легко) / 48
  (Средне) / 108 (Сложно) / 216 (Эксперт) деталей — те же пресеты, что
  были в форме загрузки раньше, но теперь `pieces` в query не выбирают:
  `POST /api/puzzles` заводит все четыре строки `puzzles` одним
  запросом, каждая — свой `id`/сетка/случайный `seed` (формы деталей
  должны отличаться между вариантами), но общий файл картинки
  (`image_file`, уникальный на загрузку — `crypto.randomUUID()` в
  имени) и общий `owner_user_id`.
- **Группировка вариантов — без новой колонки в схеме**: одинаковые
  `image_file`+`owner_user_id` у всех четырёх строк достаточно, чтобы
  клиент (`groupPuzzles` в `assets/app.js`) собрал их в одну карточку с
  рядом кнопок сложности вместо одной кнопки «Играть». Отдельный
  `group_id` не заводили — меньше состояния для того же результата.
  Тот же приём останется рабочим и для публичных пазлов, когда до
  публикации дойдёт очередь.
- **Приватность по владельцу**: свой пазл виден только автору в
  библиотеке (`GET /api/puzzles` фильтрует по `owner_user_id`, `NULL` —
  встроенные пазлы, видны всем). Файл при этом отдаётся по
  непредсказуемому (`crypto.randomUUID()`) URL без проверки членства —
  тот же компромисс, что у публичных фото Trip: не перечисляемо, но не
  требует тащить список участников комнаты на каждый байт картинки.
  Ради этого решения `sessionSummary` отдаёт вложенный `puzzle`-объект
  внутри сеанса — так остальные участники комнаты видят метаданные и
  URL приватного пазла хозяина сеанса, не имея доступа к его личной
  библиотеке.
- **Сетка — из соотношения сторон** присланного клиентом изображения
  (`gridForPieceTarget`) и целевого числа деталей: сервер не декодирует
  картинку сам, доверяет `w`/`h` от клиента — они влияют только на то,
  насколько квадратными выглядят детали.
- **Сжатие на клиенте**: `createImageBitmap` + `<canvas>`, потолок
  большей стороны 2000px, JPEG 0.86 — сервер сохраняет присланные байты
  как есть.
- **Тип файла — по магическим байтам** (`sniffImage`/`PHOTO_MIME`,
  тот же приём, что в `Trip/server.js`), не по `Content-Type` от
  клиента.
- **Хранение на диске**, не в SQLite: `DATA_DIR/puzzle-photos/`, тот же
  принцип, что у `Trip`'s `PHOTO_DIR`.
- **Удаление — целой группой**: пользователь думает о загруженном фото
  как об одной вещи, не как о четырёх строчках. Удаление любого
  варианта чистит всю группу (`stmt.puzzlesByImage`, по
  `image_file`+`owner_user_id`) и файл на диске один раз. Если хоть
  один вариант группы уже засветился в комнате
  (`room_sessions.puzzle_id`) — блокируется удаление всей группы, `409`.

### Свои заявки и уведомления

Страница профиля (`/profile/:id`) — публичная витрина ОДОБРЕННОГО, но
своему автору она же показывает отдельным блоком «На модерации» то, что
он отправил и по чему модератор ещё не ответил (`pending` в
`GET /api/users/:id/puzzles`). Сервер отдаёт этот список только самому
владельцу профиля (сверка по токену) — гость и любой другой вошедший
видят `pending: []`, непроверенное фото в чужую витрину не протекает.
Карточки там `openable:false` (см. `buildCard`) — открывать нечего, свой
ещё не одобренный пазл вне комнаты всё равно упрётся в «пазлы из своих
фото собираются только в комнатах»; меню «…» остаётся, отозвать заявку
удалением можно.

Уведомления о результате модерации (общий канал Auth, см.
`Auth/INTEGRATION.md`) показываются в модалке аккаунта ТОЛЬКО пока не
прочитаны: список рисуется из непрочитанных, а помечаются они разом в
тот момент, когда человек раскрыл колокольчик — не при открытии модалки
(список грузится ещё свёрнутым, и это был бы не просмотр) и не по клику
по каждому. С экрана они при этом не исчезают сию секунду — уходят при
следующем открытии: убирать строки из-под курсора, пока их читают, —
худшее из возможных поведений. Архива уведомлений у сервиса нет: это
разовые «вам ответили по такой-то заявке», а не переписка.

## Загрузка через Admin

Реализация откладывается, но архитектура должна её учитывать: Admin
должен иметь возможность закинуть картинку в библиотеку сервиса —
это будут дефолтные пазлы, доступные без входа.

Существующий `Shared/admin-internal.js` устроен под чтение (Admin
дёргает `/internal/logs` у сервиса), а тут нужна запись в обратную
сторону (Admin → Puzzle отправляет файл). Скорее всего это отдельный
`/internal/puzzles` с тем же `ADMIN_INTERNAL_KEY`-протоколом, но сам
эндпоинт и приём файла — не по образцу, проектировать заново.

### Временно скрыть пазл

У каждой строки в библиотеке Admin есть «Скрыть» — мягкая мера рядом с
«Удалить», на случай «пока уберём, потом решим». Пазл пропадает из всех
публичных списков (библиотека, страница категории и счётчик у неё,
профиль автора, полоса «Продолжить сборку», `sitemap.xml` и SSR-снимки),
а его страница `/puzzle/:id` продолжает открываться, но отдаётся с
`<meta name="robots" content="noindex">` — иначе порвались бы комнаты, в
которые пазл уже добавили, и чужие ссылки. Рейтинг, прогресс сборки и
начатые сеансы за столом не трогаются вовсе и возвращаются вместе с
пазлом по кнопке «Вернуть» — этим скрытие и отличается от удаления,
которое унесло бы их за собой.

Флаг — `puzzles.hidden_at` (время, а не 0/1: у «временной меры» хочется
видеть, сколько она уже длится), общий для всей группы `image_file`, как
категория и пометка «не для детей». Переключается через
`POST /internal/puzzles/:id/hidden` c `{"hidden": true|false}`; в
`/internal/puzzles` скрытые ОСТАЮТСЯ (с полем `hidden`) — иначе их нечем
было бы вернуть. Для контента, который нельзя оставлять на сервисе, это
не замена удалению.

### Письма о результате модерации

`notifyPublishOutcome` (см. `server.js`) шлёт автору письмо через
`lib/mailer.js` — Resend, тот же приём и тот же секрет, что у Auth и Trip.
**На сервере нужен `RESEND_API_KEY` в `.env` рядом с compose** (тот же
файл, что и `ADMIN_INTERNAL_KEY`); `docker-compose.prod.yml` прокидывает
его и `MAIL_FROM` внутрь контейнера. Без ключа письма не уходят вовсе:
mailer печатает «письмо не отправлено» в stdout и возвращает
`{ok:false}`, а одобрение при этом проходит как обычно — со стороны это
выглядит как «уведомление в аккаунте пришло, письма нет». Ровно так и
случилось: этих двух строк в compose какое-то время просто не было.

Чтобы такое больше не приходилось выяснять по stdout, отсутствие ключа
видно сразу при старте (`[!] Не задан RESEND_API_KEY …` в логе контейнера —
предупреждение, не падение: письма необязательны для работы сервиса), а
исход каждого письма пишется в журнал (`adminLog`, вкладка «Логи» в Admin)
с НАЗВАННОЙ причиной: отправлено; не задан `RESEND_API_KEY`; Resend
ответил ошибкой (её текст рядом — чаще всего домен из `MAIL_FROM` не
подтверждён в Resend); не достучались до Resend; автор снял галочку
«прислать письмом»; у автора нет почты в аккаунте. Причину отдаёт сам
`mailer.send` полем `reason` — раньше все три внешних отказа сливались в
один `{ok:false}` и различались только по stdout. Сам адрес в журнал не
пишется — только id, название и исход.

## Комментарии к пазлам

Лента под страницей пазла (`/puzzle/:id`) и вкладка «Комментарии» в Admin.
Принятые решения (все — выбор пользователя, не умолчания):

- **Пишут только вошедшие.** Гость ленту видит, но вместо формы получает
  приглашение войти. Рейтинги, в отличие от этого, анонимные — там нечему
  быть злоупотреблением, а свободный текст от анонима это магнит для спама,
  на который нечем ответить: ни забанить толком, ни написать автору.
- **Постмодерация.** Комментарий виден сразу, лишнее сносит админ. При
  нынешней аудитории премодерация означала бы почти всегда пустую ленту и
  очередь, которую некому разбирать.
- **Уведомлений автору пазла пока нет.** Канал Auth для этого готов (см.
  `notify` в ответах approve/reject), добавить можно отдельной правкой.

Ключ — `image_file`, та же группировка, что у рейтингов: одна картинка —
один тред, общий для всех уровней сложности. Комментарии есть только у
БИБЛИОТЕЧНЫХ пазлов (`owner_user_id IS NULL`) — у чужой непроверенной
загрузки и своего черновика в комнате их нет вовсе, `/comments` отвечает
404. Автор денормализован в строку (`author_username`/`author_name`), как
`uploader_*` и `room_members`.

Удалить может автор своей реплики и админ — любую: право приходит claim'ом
`admin` в токене (см. `Auth/lib/tokens.js`), сервер отдаёт его клиенту полем
`canModerate`, и крестик появляется прямо на странице пазла, без похода в
админку. Удаление НАСТОЯЩЕЕ (`DELETE`), «мягкого» флага нет — зато текст
снесённого уходит в `adminLog` вместе с автором: иначе от комментария не
осталось бы следа, а именно он нужен, чтобы заметить, кто повторяется.

Ограничения: 1000 символов на комментарий, 20 комментариев в час на автора
(`MAX_COMMENT_LEN`/`MAX_COMMENTS_PER_HOUR`), сверх лимита — 429. В
SSR-снимок и в `sitemap.xml` комментарии НЕ попадают: пользовательский
текст на индексируемой странице — это способ занести спам прямо в выдачу,
лента рендерится только клиентом.

## GigaChat — короткие названия

Используется в двух местах: автогенерация названия при импорте с Pexels
(`gigachat.titleFromText`/`titleFromImage`) и кнопки «✨ по тексту»/«✨ по
фото» в библиотеке Admin (`/internal/puzzles/:id/title/suggest`, см.
`gigachat.js`). Разница между режимами принципиальная: «по тексту»
пересказывает существующее название, «по фото» смотрит **только на саму
фотографию** — ни старое название, ни категория в запрос не уходят. Иначе
модель пересказывает их вместо снимка, и режим теряет смысл: у фото,
импортированных с Pexels без `alt`, название вообще склеено из имени
категории (`«Библиотека 1»`, см. `Admin/assets/app.js`), так что название и
категория там — один и тот же текст. Ключ живёт **только в окружении сервера**: в браузер не
попадает, в образ не зашивается, в репозиторий не коммитится. Без
`GIGACHAT_AUTH_KEY` сервис работает как раньше, эндпоинт отвечает `503
gigachat_disabled`.

Домены Сбера подписаны корневым сертификатом Минцифры, которого нет в
alpine — без него TLS не поднимется (тот же приём, что у Trip).

### Настройка на сервере

Оба файла кладут рядом с `docker-compose.prod.yml` (то есть в `~/Puzzle/`),
в репозиторий они не попадают.

```bash
cd ~/Puzzle

# 1. Ключ — в .env рядом с compose (права 600), та же переменная,
# что ADMIN_INTERNAL_KEY.
# GIGACHAT_AUTH_KEY=ключ_из_Сбер_Студии

# 2. Корневой сертификат Минцифры.
curl -fsSL https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer \
  -o russian_trusted_root_ca.pem
chmod 644 russian_trusted_root_ca.pem

# 3. Убедиться, что файл текстовый (PEM), а не двоичный (DER):
head -1 russian_trusted_root_ca.pem   # ожидаем -----BEGIN CERTIFICATE-----

docker compose up -d
```

Имя файла должно совпадать с тем, что в `docker-compose.prod.yml`
(`russian_trusted_root_ca.pem`) — путь монтирования прописан там буквально.

**Ловушка**, в которую уже попадали: если запустить `docker compose up`
РАНЬШЕ, чем положить сам `.pem` на сервер, Docker молча создаёт на месте
bind-mount'а пустую ДИРЕКТОРИЮ вместо файла — и на хосте, и внутри
контейнера — без единой ошибки. Дальше `NODE_EXTRA_CA_CERTS` указывает на
директорию, Node её просто игнорирует, и TLS к Сберу падает с
`SELF_SIGNED_CERT_IN_CHAIN`, как будто сертификата нет вовсе. Проверка:

```bash
docker compose exec puzzle ls -la /app/certs/
# ожидаем -rw-r--r-- (файл), НЕ drwxr-xr-x (директория)
```

Если директория — `docker compose down`, `rm -rf russian_trusted_root_ca.pem`
на хосте, повторить шаг 2 выше, `docker compose up -d`.

Проверка, что всё село:

```bash
docker compose exec puzzle printenv NODE_EXTRA_CA_CERTS
docker compose exec puzzle node -e "fetch('https://gigachat.devices.sberbank.ru/api/v1/models').then(r=>console.log('TLS в порядке, ответ',r.status)).catch(e=>console.log('не вышло:',e.message))"
```

Ответ `401` — это успех: соединение установилось, а без токена и должно
быть «не авторизован». `fetch failed`/`SELF_SIGNED_CERT_IN_CHAIN` означает,
что сертификат не подхватился (см. ловушку выше).

Хватает одного корневого сертификата — промежуточный не нужен. Он
публичный, секретом не является; менять придётся, только когда Минцифры
выпустит новый — тогда достаточно заменить файл и перезапустить контейнер,
пересобирать образ не нужно.

## Миниатюры обложек

Обложки отдавались в исходном разрешении: карточка в сетке — слот 318×238
(`.puzzle-card-thumb`, `aspect-ratio:4/3` + `object-fit:cover`), а грузилось
в неё фото 1880×1253, то есть примерно в 35 раз больше пикселей, чем
показывается. Замеры на живом сайте: главная — 3.5 МБ за заход (2.8 МБ из
них картинки), `/category/cats` — 3.9 МБ на 21 обложку, отдельные файлы по
300–490 КБ. Вёрстку это не ломало (слот фиксированный, сдвига разметки нет),
ломало скорость — и через неё поведенческие, которые для Яндекса весят
больше, чем любая разметка.

Решение: сервис держит рядом с оригиналом две пережатые копии и отдаёт в
карточки их.

- **Три размера: 400, 640, 800.** Белый список в `lib/thumbs.js`, не
  произвольное число из адреса: иначе любой желающий заставил бы сервис
  пережимать одну картинку под сколько угодно размеров. Что выбирает
  браузер при `sizes="(max-width: 30rem) 92vw, 320px"` — замерено в
  браузере, а не выведено на бумаге:

  | экран | слот | берёт |
  |---|---|---|
  | обычный, DPR 1 | 286–318px | 400w |
  | retina, DPR 2 | 286px | **640w** |
  | телефон 375px, DPR 2 | 340px | 800w |

  Ступень 640 добавлена после замера живой главной: там самые тяжёлые
  картинки были 84–127 КБ, потому что при DPR 2 браузеру приходилось брать
  800w — ближайшее, что было. На телефоне 800w остаётся и остаётся честным
  выбором: сетка там в одну колонку (`minmax(15.5rem,1fr)`), карточка
  шириной почти во весь экран, 340×2 = 680 физических пикселей реально
  нужны. Облегчить мобильную главную можно было бы двумя колонками вместо
  одной, но это решение про вид сетки, а не про миниатюры.

  800 нужен и сам по себе — для превью в модалках и картинки на
  `/puzzle/:id` (`previewSrc`), так что отдельной ступени под них не надо.
- **Оригинал остаётся за столом.** Из него нарезаются детали
  (`createPieceEl`), миниатюра там дала бы мыло. Превью рядом со столом тоже
  берёт оригинал — он к этому моменту уже в кэше браузера под детали.
- **Адрес без расширения** — `/uploads/thumb/400/<uuid>`. На диске миниатюра
  бывает и `.webp` (vips в проде), и `.jpg` (sips на macOS при локальной
  разработке); формат браузеру сообщает `Content-Type`, он и так главнее
  расширения, а адрес от того, какой инструмент нашёлся на машине, не
  зависит и не меняется при переезде dev → прод.
- **Пережимает внешняя программа, не Node.** Декодировать JPEG стандартной
  библиотекой нечем, а npm-зависимость сломала бы главное свойство сервиса —
  зависимостей нет вовсе. Системный бинарник этого свойства не трогает: это
  зависимость образа (`apk add --no-cache vips-tools`, одна строка в
  Dockerfile), а не кода. Выбран vips, а не imagemagick — вчетверо меньше в
  образе и быстрее на ровно этой задаче. `lib/thumbs.js` ищет по PATH
  `vips` → `vipsthumbnail` → `magick` → `convert` → `sips`, так что
  локально на macOS ставить ничего не нужно.
- **Без vips сервис работает.** Нет инструмента, битый файл, нет места — по
  адресу миниатюры отдаётся ОРИГИНАЛ, с коротким `Cache-Control` вместо
  `immutable`. Страница выглядит как до правки, просто тяжёлой; сломанного
  `<img>` не бывает никогда. Этим же отличием в заголовке тест и определяет,
  какой путь отработал, не разбирая байты картинки.
- **Генерация ленивая + разовый прогрев.** Миниатюры заводятся при загрузке
  фото (оба входа — `POST /api/puzzles` и `POST /internal/puzzles`), а для
  уже лежащих ~480 обложек — на первый запрос. Отдельная миграция перед
  деплоем поэтому не нужна, но первое пережатие попадёт в ответ живому
  посетителю, причём залпом (Яндекс обходит категории подряд, по два десятка
  картинок на каждой). Поэтому сразу после деплоя:

      docker compose exec puzzle node scripts/backfill-thumbs.mjs

  Скрипт идемпотентен, базу не трогает вовсе — идёт по файлам в каталоге
  оригиналов. `--force` пережимает заново (нужно, если поменялись размеры
  или качество).
- **Лежат в томе.** `DATA_DIR/puzzle-thumbs/<размер>/<uuid>.<ext>`, рядом с
  `puzzle-photos`; том монтируется на `DATA_DIR` целиком, так что миниатюры
  переживают пересоздание контейнера. Отдельный каталог, а не подкаталог
  внутри `puzzle-photos` — тот отдаётся по `/uploads/` по basename с
  проверкой расширения, и подкаталог там пришлось бы отдельно исключать.
  Удаление пазла уносит и миниатюры.

### Почему это не заработало с первого раза

Первый прод с миниатюрами отдавал по их адресам оригиналы — то есть всё
время срабатывал фолбэк. В журнале было `[thumbs] не удалось сделать
миниатюру … vips вернул 1` на каждой картинке. Три ошибки, все мои:

1. **`.part` в конце имени убивал определение формата.** И vips, и
   ImageMagick выбирают формат записи по суффиксу выходного файла, а имя
   было `<uuid>.webp.123.part`. Формата `.part` vips не знает — ошибка.
   Теперь `.part` вставляется перед расширением: `<uuid>.123.part.webp`.
2. **Опция сохранения `strip`.** В libvips 8.15+ она объявлена устаревшей в
   пользу `keep`, а неизвестную опцию vips считает ошибкой, не
   предупреждением. Просто убрана: выбрасывать метаданные из картинки в
   400px смысла почти нет, а без опции команда работает на любой версии.
3. **`stdio: "ignore"` выбрасывал stderr.** Поэтому в журнале оставалось
   одно «vips вернул 1» без причины, и разбираться пришлось гаданием.
   Теперь stderr читается и его последние строки идут в то же сообщение.

Отдельно стоит запомнить, почему это не поймалось локально: на macOS
инструментом оказывается `sips`, а он на неизвестное расширение только
ругается предупреждением и всё равно пишет файл. То есть локально
«работало», в контейнере не работало ничего. Расширение временного файла
теперь закреплено тестом (`partPathFor`), а не только внимательностью.

После починки нужен перезапуск контейнера: неудачи кэшируются в памяти до
рестарта (см. `failed` в `lib/thumbs.js`), иначе сервис продолжит отдавать
оригиналы по уже «запомненным» адресам.

Замер на настоящей обложке библиотеки — 1880×1253, 313 КБ JPEG:

| что отдаётся | размер | JPEG (sips, локально) | WebP (vips, прод) |
|---|---|---|---|
| оригинал (было) | 1880×1253 | 313 КБ | — |
| `thumbUrl`, обычный экран | 400×266 | 21 КБ | **7 КБ** |
| `previewUrl`, retina и телефон | 800×533 | 79 КБ | **22 КБ** |

То есть карточка в сетке становится легче в 45 раз на обычном экране и в 14
раз на retina. В пересчёте на страницы: главная грузила 13 обложек выше
сгиба на 2.8 МБ — станет около 90 КБ и 290 КБ соответственно;
`/category/cats` грузила 21 обложку на 3.9 МБ — станет около 150 КБ и 460 КБ.

Проверка в тестах не про байты, а про контракт: что по адресу миниатюры
всегда приходит рабочая картинка, что 400px заметно легче оригинала, что
непережимаемый файл отдаётся оригиналом с коротким кэшем и что размер не из
белого списка миниатюрой не отдаётся. Сравнение «миниатюра легче» на
синтетическом шуме врало бы (JPEG сжимает шум хуже PNG, уменьшенная копия
выходила БОЛЬШЕ оригинала) — поэтому фикстура градиентная, см.
`gradientPng` в `test/e2e-rooms.mjs`.

Чего эта правка НЕ исправила, хотя рядом: любой неизвестный путь (включая
`/uploads/thumb/<не тот размер>/…`) по-прежнему отдаёт главную страницу с
кодом 200, а не 404. Это отдельная задача, см. «Открытые вопросы».

## Версия статики в адресе

Имена файлов в `assets/` без хэша, а отдавались они с `max-age=3600`.
Значит **до часа после каждого деплоя посетитель работал на старом
`app.js` с новым сервером**. Обычно это просто «новое не включилось», но
один раз вышло хуже: правка «Кэш и вес списка библиотеки» убрала `thumbUrl`
из ответа `/api/puzzles` (новый клиент считает адрес сам), а старый клиент
из кэша на отсутствие поля подставлял `p.imageUrl` — то есть час грузил
обложки по 300 КБ вместо 15 КБ, ровно то, что чинилось.

Поймано измерением живого сайта: `srcset` на странице был из двух ступеней,
хотя свежий `app.js` отдавал три. Сначала я решил, что ступень 640 не
доехала, — а доехала, просто браузер держал старый скрипт.

Теперь в `index.html` адреса статики проштампованы `?v=<версия>`:

| что просят | кэш |
|---|---|
| `/assets/app.js?v=<текущая>` | `max-age=31536000, immutable` |
| `/assets/app.js` без версии | `max-age=3600` |
| `/assets/app.js?v=<старая>` | `max-age=3600` |

`immutable` безопасен именно потому, что ключ кэша включает query: сборка
поменяет версию, адрес станет другим, а старый просто никому больше не
понадобится. На адресе без штампа ставить `immutable` было бы ошибкой —
содержимое под ним деплой меняет; туда попадают `/favicon.ico` с корня,
старый HTML из чьего-то кэша и прямые заходы.

Побочная польза: постоянные посетители перестают каждый час заново качать
139 КБ `app.js` и 44 КБ CSS.

Решения:

- **Версия считается на каждый запрос страницы**, а не один раз при старте.
  Это 18 `statSync` рядом с чтением самого `index.html`, то есть бесплатно,
  зато в разработке правка `app.js` сразу меняет версию. Со стартовым
  кэшированием было бы наоборот: `immutable` на год плюс неизменный `?v=`
  — своё же изменение не увидеть без принудительной перезагрузки.
  Закреплено тестом: правка файла в `assets/` меняет версию без
  перезапуска сервера.
- **По mtime и размеру, а не по содержимому**: хэшировать 640 КБ
  `app.js`+`styles.css` на каждый запрос расточительно. Плата — деплой, не
  менявший содержимое, всё равно сбросит кэш (в новом образе новые mtime).
  Это одна лишняя загрузка ~190 КБ на посетителя за деплой и ошибка в
  безопасную сторону: сбросить кэш лишний раз не страшно, не сбросить —
  та самая дыра.
- **Штамп накладывается последним**, уже по готовому HTML: `applySeoOverride`
  ищет в нём точные строки, включая абсолютный `og:image` с `/assets/`
  внутри. Поэтому регулярка привязана к кавычке и относительному пути
  (`src="/assets/…"`), а абсолютный `og:image` не трогается — иначе подмена
  картинки пазла молча перестала бы находиться. Отдельная проверка в тестах.
- **`assets/puzzles/*.svg` в версию не входят** и штампа не получают: это
  содержимое библиотеки, а не код, оно меняется отдельно от сборки.

## Кэш и вес списка библиотеки

`GET /api/puzzles` без `roomId` отдавал всю библиотеку на каждый заход
главной: **4157 строк, 2.5 МБ JSON (211 КБ в gzip)**. И собиралось это
заново на каждый запрос — 4157 объектов, подзапрос рейтинга на каждую
уникальную картинку и `JSON.stringify` на 2.5 МБ, синхронно, в том же
потоке, что и всё остальное (`node:sqlite` — `DatabaseSync`). Клиент при
этом рисует 48 карточек за раз (`PUZZLE_PAGE_SIZE`).

Сделано два изменения:

**1. Ответ собирается один раз и переиспользуется**, пока в базе ничего не
менялось, плюс `ETag` и ответ `304` на условный запрос. Прежний
`Cache-Control: no-store` из `json()` запрещал браузеру даже спрашивать —
теперь `no-cache`, то есть «кэшируй, но каждый раз проверяй». Повторный
заход и обычный F5 получают 304 без тела вовсе.

Версия кэша — встроенная функция SQLite `total_changes()`: счётчик
изменённых строк за время жизни соединения. Любой `INSERT`/`UPDATE`/`DELETE`
где угодно в процессе его двигает, а чтения — нет. Выбрано именно так, а не
ручной вызов инвалидации в каждом месте записи: мест этих много (две
загрузки, три удаления, смена названия, категории, пометки «не для детей»,
скрытие, модерация, оценки), и забытое означало бы тихо устаревший список у
всех посетителей. Тут забывать нечего — счётчик двигает сама запись. Цена:
кэш сбрасывается и от записей, к библиотеке не относящихся (прогресс
сборки, комнаты), но список читают только при загрузке страницы, так что
это бесплатно.

**2. Из списка убрано лишнее**: поля со значением `null` (клиент проверяет
их только на правдивость), `notForKids: false` и выводимые из `imageUrl`
`thumbUrl`/`previewUrl` — два адреса на строку × 4157 строк это 580 КБ,
целиком вычислимых из третьего поля. Клиент их теперь считает сам
(`thumbFromImageUrl`), причём сначала смотрит, не прислал ли сервер готовый:
в одиночных ответах и в списке комнаты поля остались, и обе формы работают.

Облегчение применяется **только к списку библиотеки** (`libraryPayload`).
Одиночные объекты и список комнаты идут через `puzzlePayload` как есть —
там экономить нечего.

Замер на реальных данных прода:

| | байт | gzip |
|---|---|---|
| было | 2 563 537 | 211 270 |
| стало | 1 378 491 | 193 810 |
| повторный заход | — | **0 (304)** |

Сырой payload — **−46%**, по сети — только −8%: повторяющиеся имена полей и
похожие URL gzip жмёт прекрасно, так что экономия байтов в основном
достаётся браузеру, а не сети. Но вдвое меньше работы на разбор JSON и
вдвое меньше памяти под него — а это как раз телефон, на котором и так
тяжело. Главный же выигрыш — третья строка таблицы.

### Чего здесь нет: настоящей пагинации

Намеренно. Клиенту весь список нужен не для сетки, а для вещей, которые
считаются по всей библиотеке сразу: нумерация «Категория #N»
(`ensureDisplayTitleCache`), «Продолжить сборку» у гостя (прогресс лежит в
localStorage, сервер о нём не знает), сортировка, фильтр по категории и блок
«похожие». Серверная пагинация потребовала бы переписать всё это — см.
«Открытые вопросы».

## Честный 404

До этой правки **любой** путь отдавался с кодом 200 и телом главной
страницы: `/blog`, `/nonexistent`, `/puzzle/<несуществующий>`,
`/category/<нет такой>`, `/yandex_12345.html`. Для поиска это soft-404 —
Яндекс отдельно это диагностирует, жжётся краулинговый бюджет, а любая
внешняя ссылка на произвольный путь заводила ещё одну «страницу»-копию
главной, которую нечем вывести из индекса.

Что теперь:

| адрес | было | стало |
|---|---|---|
| `/`, `/categories`, `/rooms`, `/publish` | 200 | 200 |
| `/puzzle/:id`, `/category/:slug` — существующие | 200 | 200 |
| `/puzzle/:id` — нет такого, чужой или приватный | 200 + главная | **404** |
| `/category/:slug` — нет такой или не одобрена | 200 + главная | **404** |
| `/blog`, `/nonexistent`, `/puzzle/a/b` | 200 + главная | **404** |
| `/yandex_*.html` — файла нет | 200 + главная | **404** |
| `/room/:id`, `/rooms/join/:code`, `/profile/:login` | 200 | 200 + **noindex** |
| `/index.html` | 200, дубль `/` | **301 → `/`** |
| `/categories/` и любой хвостовой слеш | 200, дубль | **301** без слеша |

Решения, которые стоит знать:

- **Тело при 404 — тот же каркас приложения.** Клиентский роутер должен
  подняться и нарисовать «Страница не найдена» (см. `renderNotFound` в
  `assets/app.js`), иначе человек по устаревшей ссылке увидел бы голый текст
  вместо сайта. Поиску достаточно кода ответа. Текст на сервере и у клиента
  дословно одинаковый — расхождение между тем, что видит краулер, и тем, что
  видит человек, мы только что вычистили на страницах пазлов, незачем
  заводить его здесь.
- **Решение устроено «от противного»**: 404 получает всё, для чего ни одна
  ветка `serveApp` не собрала настоящую страницу. Отдельного списка
  существующих маршрутов нет намеренно — он был первой версией правки и сразу
  разошёлся с реальностью: список проверял id как `[^/]+`, а разбор пути — как
  `[\w-]+`, и `/puzzle/<кириллица>` (приходит percent-encoded, с процентами в
  пути) попадал в «маршрут существует», но ни в одну ветку разбора, то есть
  снова 200. Поймано тестом. Одна точка истины — сам разбор.
- **Приватный пазл — 404, а не 403.** По угаданному id наружу не должно
  утекать даже то, существует ли такая строка. Хозяин своё фото всё равно
  увидит: клиент поднимется и спросит API со своим токеном (тот же критерий,
  что у самого API).
- **Скрытый из библиотеки пазл (`hidden_at`) остаётся 200 + noindex**, как и
  был: прямая ссылка должна открываться, а из индекса его убирает noindex.
- **Комнаты, приглашения, профили — 200 + noindex.** Существуют они или нет,
  сервер без токена сказать не может. `robots.txt` их не закрывает и не
  должен: закрытое в robots Яндекс всё равно показывает строкой «страница
  заблокирована», а noindex убирает совсем.

### ⚠ Подтверждение прав в Яндекс.Вебмастере — проверьте перед деплоем

До этой правки `/yandex_<любые символы>.html` отдавался с кодом 200, то есть
сайт «подтверждал» права по **любому** такому адресу, не имея ни одного
такого файла. Если в Вебмастере выбран способ «HTML-файл», подтверждение
держалось на этой случайности и при следующей перепроверке слетит.

Что делать: посмотреть в Вебмастере способ подтверждения. Если это файл —
положить настоящий файл в корень репозитория рядом с `index.html` и добавить
его в `COPY` в Dockerfile (`serveStatic` отдаёт `yandex_*.html` и
`google*.html` по маске, но **только если файл реально есть на диске**).
Надёжнее переключиться на метатег или DNS — они не зависят от сборки.

### Каноникал стола

У `/table/:id` и `/puzzle/:id` были дословно одинаковые
title/description/h1 и у каждого свой self-canonical — то есть на каждую
картинку в индексе претендовали два адреса с одинаковым содержимым. Теперь
каноникал и `og:url` стола ведут на `/puzzle/:id`. Стол остаётся рабочим и
открывается по прямой ссылке, просто в выдаче его представляет страница
пазла — там есть и описание, и уровни сложности, и комментарии. `og:url`
туда же: при пересылке в мессенджер человеку нужна страница пазла, а не
сразу стол.

### Найдено честным 404: PWA-манифест не работал никогда

`manifest.json` не был ни в `ROOT_FILES` (`server.js`), ни в `COPY`
Dockerfile. `<link rel="manifest" href="/manifest.json">` уходил в
`serveStatic`, тот его не находил, запрос проваливался в `serveApp` и получал
**код 200 с телом главной страницы** и `Content-Type: text/html`. Браузер
молча не мог его разобрать.

Проверено на живом сайте: `curl https://puzzle.burninghouse.ru/manifest.json`
отдавал `<!doctype html>`. То есть PWA-манифеста у сервиса не было с самого
начала, а вместе с ним не работала и кнопка «Установить как приложение» — ей
нужен `beforeinstallprompt`, а его без валидного манифеста браузер не
присылает. Именно так soft-404 и прячет поломки: отличить «файла нет» от
«вот вам главная вместо него» по коду ответа было нельзя.

Исправлено в трёх местах: `ROOT_FILES`, `COPY` в Dockerfile и проверка
наличия файлов на этапе сборки. Регрессия закреплена тестом (200 +
`application/json` + разбор JSON).

## Текст на страницах пазлов и категорий

До этой правки `/puzzle/:id` отдавала в исходном HTML заголовок и одно
предложение — около 90 символов своего текста на 2500 общих (шапка, футер,
блок FAQ). На 477 страницах это 477 почти одинаковых документов, а такие
Яндекс держит в индексе неохотно («малоценные или маловостребованные
страницы»). Вторая беда той же страницы: для краулера она была тупиком — ни
одной ссылки дальше по сайту, кроме общей навигации. Видимые крошки и блок
«похожие» рисует только JS, а разметка `BreadcrumbList` обещала поиску
ссылку на категорию, которой в HTML не было.

Что теперь в исходном HTML страницы пазла:

- **Видимые крошки** со ссылкой на категорию — те же, что рисует клиент, и
  те же, что уже уходили в `BreadcrumbList`.
- **Уровни сложности той же картинки** — реальные ссылки на существующие
  `/puzzle/:id` (у каждого уровня свой id). Для человека это выбор
  сложности, для краулера — связный куст страниц вместо 477 одиночек.
  Текущий уровень ссылкой на себя же не идёт.
- **Комментарии** — единственный текст на странице, написанный людьми, и
  потому самый ценный. Без формы ответа: её поставит JS.
- **Другие пазлы категории** — те же шесть, что показывает клиент.
- **Вводный абзац из данных**: число деталей, сетка, ориентация (считается
  по сетке — она от пропорций фото и строится, см. `gridForPieceTarget`),
  диапазон уровней сложности, категория ссылкой, средняя оценка.

Своего текста в `<main>` стало 650+ символов вместо ~90, внутренних ссылок —
12 вместо нуля. Ничего из этого не выдумано и не размножено шаблоном ради
объёма: все числа из базы, поэтому у каждой страницы текст свой настолько,
насколько своим является сам пазл.

Чего по-прежнему НЕТ — живого описания самой фотографии. Оно требует либо
рук, либо GigaChat (`gigachat.js` уже умеет смотреть на картинку, см.
`titleFromImage`), и это отдельная задача, см. «Открытые вопросы».

### FAQ — только на главной

Блок лежит в статичном `index.html`, то есть уезжал в каждую из 500+
страниц. У Google на это прямое правило: FAQ-разметка, повторённая по всему
сайту, расширенного сниппета не даёт вовсе — и по смыслу верно, вопросы
«нужна ли регистрация» и «сколько стоит» относятся к сервису, а не к
странице конкретного пазла.

- **Разметку** `FAQPage` снимаем со всех не-главных страниц —
  `applySeoOverride` зовётся только для них, так что проверять путь не
  нужно. Выкусывание поблочное (`dropJsonLd`), через колбэк по каждому
  `<script type="application/ld+json">`: блоков в `<head>` несколько
  (WebSite, FAQPage, иногда BreadcrumbList), и ленивый `[\s\S]*?` в одном
  регэкспе «от script до @type» спокойно перепрыгнул бы границу чужого
  блока и унёс бы его целиком.
- **Видимый блок** убираем только на страницах пазлов (`dropFaq` в вызове):
  там он составлял бóльшую часть всего текста. На `/categories`,
  `/category/:slug`, `/rooms` и `/publish` он остаётся — страниц этих
  единицы, дублированием текста их не топит, а человеку в футере он не
  лишний. **Это видимое изменение:** в футере страницы пазла гармошки
  «Частые вопросы» больше нет.

### Заголовок страницы пазла

Сервер отдавал `<h1>Пазл «Холмы»</h1>`, а клиент после гидратации заменял
его на вычисляемое «Природа #1» (`puzzleDisplayTitle`). Поиск сравнивает
исходный HTML с отрендеренным, и разный текст в одном и том же h1 ему не
нравится — тем заметнее теперь, когда на странице появился настоящий текст и
h1 весит больше.

Выровнено в сторону настоящего названия: в **сетке** карточек нумерация
«Категория #N» осмысленна (однородные подписи у похожих картинок одной
категории), а на **собственной странице** пазла полезнее его имя. Категорию
человек тут всё равно видит — `.puzzle-page-tag` рядом с заголовком.
Формулировка у клиента дословно серверная, вместе со словом «Пазл» и
кавычками: сравнивается текст узла, и «Холмы» против «Пазл «Холмы»» было бы
тем же расхождением, только тише. Заголовок блока похожих выровнен тем же
способом («Другие пазлы в категории «X»» вместо «Ещё в категории «X»»).

Строка закреплена тестом с двух сторон: формат серверного h1 проверяется
дословно, и в комментарии там сказано, что парная строка живёт в
`renderPuzzlePage`. Меняете одну — меняйте вторую.

Попутно у `titleEn` появился первый читатель на клиенте: GigaChat заводит
его давно (см. `gigachat.js`), а интерфейс не использовал вовсе — теперь при
английском интерфейсе заголовок и `<title>` берут его, если он есть.

#### Защита от непрезентабельных названий

Выравнивание h1 сразу же показало, что названия в библиотеке бывают двух
сортов. Короткие человеческие («Холмы», «Снежные вершины», «Элегантный
интерьер классической библиотеки Манчестера») — их придумал GigaChat при
импорте или человек при публикации. И сырой alt-текст с фотостока, попавший
в базу, пока до него не дошла очередь переименования:

> Пазл «Stunning aerial view of Progreso Beach, Yucatan, Mexico at sunset, showing the s»

Замер по живой базе на момент правки: **239 названий первого сорта и 238
второго** из 477. В сетке карточек разницы не видно — там подпись всегда
«Категория #N», — а в h1 и `<title>` она видна, и очень.

Настоящее лечение — дочистить данные: `scripts/rename-pexels-titles.mjs`
переименовал половину библиотеки и просто не был доведён до конца
(`--limit`). Но при следующем импорте GigaChat может быть не настроен или
отказать, и в базу снова ляжет длинный alt — в `POST /internal/puzzles` это
сознательно НЕ ошибка, а ухудшение названия. Поэтому правило, а не только
разовая миграция:

- `isPresentableTitle(title)` — не длиннее 60 символов и латиницы не больше
  половины букв. Доля, а не «есть хоть одна латинская буква»: в нормальном
  названии латиница попадается («Кафе Cafe de Flore»).
- Не прошло — в заголовке, `<title>`, `description`, `alt` и крошках
  показывается та же подпись, что в сетке карточек: «Категория #N». Нет и
  номера (пазл без категории, публикация пользователя) — остаётся название:
  лучше неидеальное, чем ничего.
- Правило проверено на живой базе: латиница отсекает ровно те 238, длина не
  отсекает ни одного хорошего (самое длинное кириллическое — 54 символа).
- **Правило дублируется** в `server.js` и `assets/app.js`. Расходиться им
  нельзя — на этом держится совпадение h1 до и после гидратации. Тест
  сверяет, что функция есть по обе стороны и порог одинаковый; общего модуля
  между сервером и клиентом в проекте нет, и ради шести строк он не нужен
  (тот же случай, что `pluralRu`/`plural`).

Заодно починена нумерация. Номер «Категория #N» теперь считает один
`categoryPuzzleNumbers` — по **полному** списку категории, включая
помеченные «не для детей». Раньше статичный список категории фильтровал их
**до** нумерации, а клиент (он берёт `/api/puzzles`, где такие пазлы есть)
нумеровал вместе с ними: в категории с одним «не для детей» в середине все
последующие номера у сервера и у клиента расходились на единицу. Фильтр
остался, но решает теперь только, **что** рисовать, а не **как** нумеровать
— скрытая картинка забирает свой номер с собой, и в списке виден пропуск.

### Английский интерфейс не стартовал

Найдено при проверке h1 на английском. Вызов `applyTheme()` на верхнем
уровне `assets/app.js` стоял **до** словаря `EN`: `applyTheme` ставит подпись
кнопки темы через `t()`, а `t()` при английском интерфейсе читает `EN` —
`const`, то есть TDZ. С `puzzle_lang=en` скрипт падал на этой строке ещё до
роутера с `Cannot access 'EN' before initialization`, и приложение не
стартовало вовсе: страница так и оставалась серверной заглушкой.

На русском этого не видно — `t()` при `getLang()==="ru"` до `EN` не
дотягивается и возвращает оригинал. Этот же вызов уже один раз переезжал по
той же причине (тогда из-за `LANG_KEY`) и остановился на полпути: за
`LANG_KEY`, но всё ещё перед `EN`. Теперь он после `EN_END`, и порядок
закреплён проверкой в `test/e2e-rooms.mjs` — браузера в тестах нет, поэтому
проверяется порядок в исходнике.

### Категории

У 33 категорий на всю разницу было одно предложение «N пазлов в категории
«X» — собирайте онлайн бесплатно», то есть страницы отличались друг от
друга названием и числом. Теперь во вводном абзаце ещё и диапазон
сложности из базы, а число пазлов попало и в `<meta name="description">` —
в сниппете выдачи это первое, что человек читает про страницу. Заодно это
единственные ссылки с категории на `/rooms` и `/publish`: до них путь с
этих страниц у краулера был только через общую навигацию в шапке.

## Открытые вопросы для будущих задач

- **Серверная пагинация библиотеки.** Сейчас `GET /api/puzzles` отдаёт все
  4157 строк (см. «Кэш и вес списка библиотеки» — вес сбит, но список
  по-прежнему целиком). Чтобы отдавать страницами, придётся перенести на
  сервер то, что клиент считает по всей библиотеке: нумерацию «Категория
  #N», сортировку, фильтр по категории, блок «похожие» и «Продолжить
  сборку» у гостя (его прогресс лежит в localStorage). Заодно напрашивается
  группировка вариантов сложности в один объект с массивом внутри: 4157
  строк — это 477 картинок по 11 уровней, и клиент их тут же группирует
  обратно (`groupPuzzles`). По замеру на данных прода это дало бы 342 КБ
  сырого / 158 КБ gzip вместо 1.38 МБ / 194 КБ.
- **Дочистить названия: 238 из 477 — сырой alt с фотостока.** В заголовки
  они уже не попадают (см. «Защита от непрезентабельных названий»), но
  подменяются на «Категория #N», а настоящее название и человеку приятнее, и
  для поиска полезнее. `scripts/rename-pexels-titles.mjs` ровно для этого и
  написан, половину библиотеки им уже переименовали. Сначала посмотреть:

      PUZZLE_BASE=https://puzzle.burninghouse.ru ADMIN_INTERNAL_KEY=... \
      GIGACHAT_AUTH_KEY=... node scripts/rename-pexels-titles.mjs --dry-run --limit=10

  Понравилось — то же без `--dry-run` и без `--limit`. Порог в скрипте — 40
  символов, у правила презентабельности — 60 и доля латиницы, так что скрипт
  заведомо захватывает всё, что правило отвергает.
- **Описание самой фотографии на странице пазла.** Текст из данных там
  теперь есть (см. «Текст на страницах пазлов и категорий»), а живого
  описания картинки — нет. `gigachat.js` уже умеет смотреть на фото
  (`titleFromImage`), так что напрашивается `descriptionFromImage` + колонка
  в `puzzles` + разовый бэкфилл по образцу `scripts/backfill-thumbs.mjs`.
- **Текст ссылок на пазлы.** В списках категорий ссылка подписана
  «Кошки #1», хотя у страницы есть настоящее название (h1 на самой странице
  уже выровнен в сторону настоящего, см. «Заголовок страницы пазла»).
  Якорный текст — один из немногих сигналов, которые мы сами себе раздаём;
  «Кошки #1» в нём не несёт ничего. Менять надо сразу в двух местах, чтобы
  исходный HTML и отрендеренный не разошлись: `categoryPuzzlesListHtml` в
  `server.js` и `puzzleDisplayTitle` в `assets/app.js`.
- Пикер друзей через Auth API для приглашения в комнату (сейчас — только
  ссылка).
- Кик/удаление участников из комнаты, presence-курсоры (не только факт
  «кто подключён», но и где именно смотрит).
- Эндпоинт и формат приёма файлов от Admin.
- Публикация своих фото в общую библиотеку (сейчас свои фото приватны и
  доступны только автору в комнатах) — следующая задача, пока не начата.
