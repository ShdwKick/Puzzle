# Что собираем?

Онлайн-сборка пазлов — одному или с друзьями. Идея зафиксирована
2026-08-23. Соло-ядро (без входа — встроенные пазлы без сохранения, со
входом — те же пазлы с прогрессом в SQLite) реализовано; дизайн
подключён (вещество бор, повадка искр interlock). Комнаты с realtime-
сборкой через WebSocket реализованы (см. «Комната» и «Стол» ниже).
Свои фото и загрузка через Admin — ещё нет, отдельными задачами. Здесь
— что решено и что ещё предстоит продумать.

Название по конвенции из `Design/services.md` — вопрос, который
спрашивают вслух, тот же приём, что у «Что смотрим?».

Домен: `puzzle.burninghouse.ru`. Аккаунты — общие, через
[BurningHouse Auth](../Auth/INTEGRATION.md); client_id для регистрации
клиента — `puzzle`, по образцу остальных сервисов.

## Идея в двух режимах

**Без входа** — доступны только пазлы из встроенного набора сервиса
(картинки грузит админ через Admin, см. ниже). Собрал и ушёл, без
сохранения между сессиями — как «Пораскинем мозгами?».

**После входа** (SSO через [`Auth`](../Auth/INTEGRATION.md), как у
остальных сервисов) — можно:
- создавать комнаты и собирать пазл с друзьями;
- загружать свои фото и делать из них пазл с настраиваемым числом
  деталей;
- прогресс сохраняется между сессиями.

## Детали пазла

Не прямоугольная сетка — детали фигурные, как в настоящих пазлах:
выступы и пазы, совпадающие у соседних деталей. Реализовано в
`assets/puzzle-shapes.js` — SVG `<path>` на деталь, форма детерминирована
по seed пазла, общее ребро у соседей строится из одних чисел в
противоположном порядке обхода, поэтому контуры совпадают без
дополнительной синхронизации.

## Комната

Реализовано: создание комнаты, список участников (роли `owner` —
создатель, остальные `member`), история прошлых сборок, библиотека
пазлов внутри комнаты (тот же список, что и в соло). Принятые решения:

- **Вход только по ссылке-приглашению** (`#/rooms/join/:joinCode`) —
  пикер друзей через Auth API сознательно не сделан в этом заходе
  (кросс-доменный CORS с `auth.burninghouse.ru` не проверен, лишняя
  внешняя зависимость).
- **Начать сборку может любой участник**, не только owner — это
  компания друзей, а не иерархия. Роль в `room_members` хранится, но
  сейчас ничем не гейтится, кроме факта членства в комнате.
- **Один активный сеанс сборки на комнату** — гарантируется частичным
  уникальным индексом в SQLite (`room_sessions`, `WHERE completed_at
  IS NULL`), повторный старт при уже активном сеансе отбивается 409.
- Кнопка «за стол» переводит из комнаты на отдельный экран стола —
  там происходит сама сборка.

## Стол

- Детали двигаются drag-and-drop, тот же код, что и в соло
  (`scatterLayout`, `createPieceEl`, фигурные детали).
- Масштабирование (zoom) и панорама — пазл на много деталей не
  поместится на экране в масштабе 1:1; камера при этом локальная у
  каждого клиента, не синхронизируется.
- **Совместная сборка в реальном времени — через WebSocket**
  (`Puzzle/ws-server.js`, голая реализация RFC 6455 поверх
  `http.Server`'s `'upgrade'`, без внешних зависимостей — в Node 22
  своего серверного WebSocket нет). WS-эндпоинт привязан к сеансу
  сборки, а не к комнате: `/ws/rooms/:roomId/sessions/:sessionId`.
  Аутентификация — токен как query-параметр (`?token=…`, браузерный
  `WebSocket` не даёт задавать заголовки), проверяется тем же
  `auth.verify()`, что и обычные API-запросы.
- Раскладка деталей не дублируется на сервере: `room_sessions.pieces`
  стартует как `NULL`, первый клиент, увидевший это в `sync`, считает
  раскладку локально и присылает `init` — сервер принимает первый
  валидный `init` как каноническую раскладку и рассылает всем; гонка
  двух одновременно открывших стол клиентов самоисцеляется.
  Позиции деталей и прогресс сборки хранятся на комнату целиком (общий
  прогресс, не свой на игрока) — персист в SQLite дебаунсится (~1.5с
  активности), финальный снап и уход последнего участника со стола
  флашатся немедленно.

## Загрузка через Admin

Реализация откладывается, но архитектура должна её учитывать: Admin
должен иметь возможность закинуть картинку в библиотеку сервиса —
это будут дефолтные пазлы, доступные без входа.

Существующий `Shared/admin-internal.js` устроен под чтение (Admin
дёргает `/internal/logs` у сервиса), а тут нужна запись в обратную
сторону (Admin → Puzzle отправляет файл). Скорее всего это отдельный
`/internal/puzzles` с тем же `ADMIN_INTERNAL_KEY`-протоколом, но сам
эндпоинт и приём файла — не по образцу, проектировать заново.

## Дизайн

Подключено: вещество — бор (зелёное пламя, `--flame-tip:#7ddf3c`,
`--flame-base:#3f6212` в `assets/styles.css`), вписано в реестр
[`Design/services.md`](../Design/services.md). Повадка искр — своя,
`interlock` (добавлена в `Shared/brand.css` рядом с settle/motes/wind/
pulse/flicker, задокументирована в
[`Design/motion.md`](../Design/motion.md)): искра блуждает вбок, как
будто ищет своё место, затем «щёлкает» на позицию вспышкой и дальше
идёт ровно вверх без блужданий — та же вспышка (в цвет пламени) играет
и на самой детали пазла при снапе на стол, так что фон и обратная связь
сборки говорят одним цветом.

Не сделано: фавикон (нужна визуальная сверка рядом с остальными пятью —
шаг чек-листа, который не проходится вслепую).

## Открытые вопросы для будущих задач

- Пикер друзей через Auth API для приглашения в комнату (сейчас — только
  ссылка).
- Кик/удаление участников из комнаты, presence-курсоры (не только факт
  «кто подключён», но и где именно смотрит).
- Свои фото в комнате.
- Ограничения на число деталей (мин/макс) и на размер загружаемого
  фото.
- Эндпоинт и формат приёма файлов от Admin.
