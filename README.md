# Что собираем?

Онлайн-сборка пазлов — одному или с друзьями. Идея зафиксирована
2026-08-23. Соло-ядро (без входа — встроенные пазлы без сохранения, со
входом — те же пазлы с прогрессом в SQLite) реализовано; дизайн
подключён (вещество бор, повадка искр interlock). Комнаты с realtime-
сборкой через WebSocket реализованы (см. «Комната» и «Стол» ниже).
Свои фото на пазл реализованы (см. «Свои фото» ниже). Загрузка через
Admin — ещё нет, отдельной задачей. Здесь — что решено и что ещё
предстоит продумать.

Название по конвенции из `Design/services.md` — вопрос, который
спрашивают вслух, тот же приём, что у «Что смотрим?».

Домен: `puzzle.burninghouse.ru`. Аккаунты — общие, через
[BurningHouse Auth](../Auth/INTEGRATION.md); client_id для регистрации
клиента — `puzzle`, по образцу остальных сервисов.

## Идея в двух режимах

**Без входа** — доступны только пазлы из встроенного набора сервиса
(картинки грузит админ через Admin, см. ниже). Собрал и ушёл, без
сохранения между сессиями — как «Пораскинем мозгами?».

**После входа** (SSO через [`Auth`](../Auth/INTEGRATION.md), как у
остальных сервисов) — можно:
- создавать комнаты и собирать пазл с друзьями;
- загружать свои фото и собирать их в комнате в 4 уровнях сложности
  (реализовано, см. «Свои фото» ниже) — только в комнатах, соло-режим
  своих фото не показывает;
- прогресс сохраняется между сессиями.

## Детали пазла

Не прямоугольная сетка — детали фигурные, как в настоящих пазлах:
выступы и пазы, совпадающие у соседних деталей. Реализовано в
`assets/puzzle-shapes.js` — SVG `<path>` на деталь, форма детерминирована
по seed пазла, общее ребро у соседей строится из одних чисел в
противоположном порядке обхода, поэтому контуры совпадают без
дополнительной синхронизации.

## Комната

Реализовано: создание комнаты, список участников (роли `owner` —
создатель, остальные `member`), история прошлых сборок, библиотека
пазлов внутри комнаты (тот же список, что и в соло). Принятые решения:

- **Вход только по ссылке-приглашению** (`#/rooms/join/:joinCode`) —
  пикер друзей через Auth API сознательно не сделан в этом заходе
  (кросс-доменный CORS с `auth.burninghouse.ru` не проверен, лишняя
  внешняя зависимость).
- **Начать сборку может любой участник**, не только owner — это
  компания друзей, а не иерархия. Роль в `room_members` хранится, но
  сейчас ничем не гейтится, кроме факта членства в комнате.
- **Один активный сеанс сборки на комнату** — гарантируется частичным
  уникальным индексом в SQLite (`room_sessions`, `WHERE completed_at
  IS NULL`), повторный старт при уже активном сеансе отбивается 409.
- Кнопка «за стол» переводит из комнаты на отдельный экран стола —
  там происходит сама сборка.

## Стол

- Детали двигаются drag-and-drop, тот же код, что и в соло
  (`scatterLayout`, `createPieceEl`, фигурные детали).
- Масштабирование (zoom) и панорама — пазл на много деталей не
  поместится на экране в масштабе 1:1; камера при этом локальная у
  каждого клиента, не синхронизируется.
- **Совместная сборка в реальном времени — через WebSocket**
  (`Puzzle/ws-server.js`, голая реализация RFC 6455 поверх
  `http.Server`'s `'upgrade'`, без внешних зависимостей — в Node 22
  своего серверного WebSocket нет). WS-эндпоинт привязан к сеансу
  сборки, а не к комнате: `/ws/rooms/:roomId/sessions/:sessionId`.
  Аутентификация — токен как query-параметр (`?token=…`, браузерный
  `WebSocket` не даёт задавать заголовки), проверяется тем же
  `auth.verify()`, что и обычные API-запросы.
- Раскладка деталей не дублируется на сервере: `room_sessions.pieces`
  стартует как `NULL`, первый клиент, увидевший это в `sync`, считает
  раскладку локально и присылает `init` — сервер принимает первый
  валидный `init` как каноническую раскладку и рассылает всем; гонка
  двух одновременно открывших стол клиентов самоисцеляется.
  Позиции деталей и прогресс сборки хранятся на комнату целиком (общий
  прогресс, не свой на игрока) — персист в SQLite дебаунсится (~1.5с
  активности), финальный снап и уход последнего участника со стола
  флашатся немедленно.

## Свои фото

Вошедший пользователь может загрузить своё фото и собрать из него
пазл — **только в комнатах**. Соло-библиотека (`#/`) своих фото не
показывает и не грузит форму загрузки вовсе; прямой переход на
`#/table/:id` для чужого/своего кастомного пазла блокируется явным
сообщением («пазлы из своих фото собираются только в комнатах»)
вместо тихой попытки собрать стол. Публикация своих фото в общую
библиотеку — отдельная будущая задача (см. «Открытые вопросы» ниже).
Принятые решения:

- **Один аплоад — сразу 4 варианта сложности**: 12 (Легко) / 48
  (Средне) / 108 (Сложно) / 216 (Эксперт) деталей — те же пресеты, что
  были в форме загрузки раньше, но теперь `pieces` в query не выбирают:
  `POST /api/puzzles` заводит все четыре строки `puzzles` одним
  запросом, каждая — свой `id`/сетка/случайный `seed` (формы деталей
  должны отличаться между вариантами), но общий файл картинки
  (`image_file`, уникальный на загрузку — `crypto.randomUUID()` в
  имени) и общий `owner_user_id`.
- **Группировка вариантов — без новой колонки в схеме**: одинаковые
  `image_file`+`owner_user_id` у всех четырёх строк достаточно, чтобы
  клиент (`groupPuzzles` в `assets/app.js`) собрал их в одну карточку с
  рядом кнопок сложности вместо одной кнопки «Играть». Отдельный
  `group_id` не заводили — меньше состояния для того же результата.
  Тот же приём останется рабочим и для публичных пазлов, когда до
  публикации дойдёт очередь.
- **Приватность по владельцу**: свой пазл виден только автору в
  библиотеке (`GET /api/puzzles` фильтрует по `owner_user_id`, `NULL` —
  встроенные пазлы, видны всем). Файл при этом отдаётся по
  непредсказуемому (`crypto.randomUUID()`) URL без проверки членства —
  тот же компромисс, что у публичных фото Trip: не перечисляемо, но не
  требует тащить список участников комнаты на каждый байт картинки.
  Ради этого решения `sessionSummary` отдаёт вложенный `puzzle`-объект
  внутри сеанса — так остальные участники комнаты видят метаданные и
  URL приватного пазла хозяина сеанса, не имея доступа к его личной
  библиотеке.
- **Сетка — из соотношения сторон** присланного клиентом изображения
  (`gridForPieceTarget`) и целевого числа деталей: сервер не декодирует
  картинку сам, доверяет `w`/`h` от клиента — они влияют только на то,
  насколько квадратными выглядят детали.
- **Сжатие на клиенте**: `createImageBitmap` + `<canvas>`, потолок
  большей стороны 2000px, JPEG 0.86 — сервер сохраняет присланные байты
  как есть.
- **Тип файла — по магическим байтам** (`sniffImage`/`PHOTO_MIME`,
  тот же приём, что в `Trip/server.js`), не по `Content-Type` от
  клиента.
- **Хранение на диске**, не в SQLite: `DATA_DIR/puzzle-photos/`, тот же
  принцип, что у `Trip`'s `PHOTO_DIR`.
- **Удаление — целой группой**: пользователь думает о загруженном фото
  как об одной вещи, не как о четырёх строчках. Удаление любого
  варианта чистит всю группу (`stmt.puzzlesByImage`, по
  `image_file`+`owner_user_id`) и файл на диске один раз. Если хоть
  один вариант группы уже засветился в комнате
  (`room_sessions.puzzle_id`) — блокируется удаление всей группы, `409`.

### Свои заявки и уведомления

Страница профиля (`/profile/:id`) — публичная витрина ОДОБРЕННОГО, но
своему автору она же показывает отдельным блоком «На модерации» то, что
он отправил и по чему модератор ещё не ответил (`pending` в
`GET /api/users/:id/puzzles`). Сервер отдаёт этот список только самому
владельцу профиля (сверка по токену) — гость и любой другой вошедший
видят `pending: []`, непроверенное фото в чужую витрину не протекает.
Карточки там `openable:false` (см. `buildCard`) — открывать нечего, свой
ещё не одобренный пазл вне комнаты всё равно упрётся в «пазлы из своих
фото собираются только в комнатах»; меню «…» остаётся, отозвать заявку
удалением можно.

Уведомления о результате модерации (общий канал Auth, см.
`Auth/INTEGRATION.md`) показываются в модалке аккаунта ТОЛЬКО пока не
прочитаны: список рисуется из непрочитанных, а помечаются они разом в
тот момент, когда человек раскрыл колокольчик — не при открытии модалки
(список грузится ещё свёрнутым, и это был бы не просмотр) и не по клику
по каждому. С экрана они при этом не исчезают сию секунду — уходят при
следующем открытии: убирать строки из-под курсора, пока их читают, —
худшее из возможных поведений. Архива уведомлений у сервиса нет: это
разовые «вам ответили по такой-то заявке», а не переписка.

## Загрузка через Admin

Реализация откладывается, но архитектура должна её учитывать: Admin
должен иметь возможность закинуть картинку в библиотеку сервиса —
это будут дефолтные пазлы, доступные без входа.

Существующий `Shared/admin-internal.js` устроен под чтение (Admin
дёргает `/internal/logs` у сервиса), а тут нужна запись в обратную
сторону (Admin → Puzzle отправляет файл). Скорее всего это отдельный
`/internal/puzzles` с тем же `ADMIN_INTERNAL_KEY`-протоколом, но сам
эндпоинт и приём файла — не по образцу, проектировать заново.

### Временно скрыть пазл

У каждой строки в библиотеке Admin есть «Скрыть» — мягкая мера рядом с
«Удалить», на случай «пока уберём, потом решим». Пазл пропадает из всех
публичных списков (библиотека, страница категории и счётчик у неё,
профиль автора, полоса «Продолжить сборку», `sitemap.xml` и SSR-снимки),
а его страница `/puzzle/:id` продолжает открываться, но отдаётся с
`<meta name="robots" content="noindex">` — иначе порвались бы комнаты, в
которые пазл уже добавили, и чужие ссылки. Рейтинг, прогресс сборки и
начатые сеансы за столом не трогаются вовсе и возвращаются вместе с
пазлом по кнопке «Вернуть» — этим скрытие и отличается от удаления,
которое унесло бы их за собой.

Флаг — `puzzles.hidden_at` (время, а не 0/1: у «временной меры» хочется
видеть, сколько она уже длится), общий для всей группы `image_file`, как
категория и пометка «не для детей». Переключается через
`POST /internal/puzzles/:id/hidden` c `{"hidden": true|false}`; в
`/internal/puzzles` скрытые ОСТАЮТСЯ (с полем `hidden`) — иначе их нечем
было бы вернуть. Для контента, который нельзя оставлять на сервисе, это
не замена удалению.

### Письма о результате модерации

`notifyPublishOutcome` (см. `server.js`) шлёт автору письмо через
`lib/mailer.js` — Resend, тот же приём и тот же секрет, что у Auth и Trip.
**На сервере нужен `RESEND_API_KEY` в `.env` рядом с compose** (тот же
файл, что и `ADMIN_INTERNAL_KEY`); `docker-compose.prod.yml` прокидывает
его и `MAIL_FROM` внутрь контейнера. Без ключа письма не уходят вовсе:
mailer печатает «письмо не отправлено» в stdout и возвращает
`{ok:false}`, а одобрение при этом проходит как обычно — со стороны это
выглядит как «уведомление в аккаунте пришло, письма нет». Ровно так и
случилось: этих двух строк в compose какое-то время просто не было.

Чтобы такое больше не приходилось выяснять по stdout, отсутствие ключа
видно сразу при старте (`[!] Не задан RESEND_API_KEY …` в логе контейнера —
предупреждение, не падение: письма необязательны для работы сервиса), а
исход каждого письма пишется в журнал (`adminLog`, вкладка «Логи» в Admin)
с НАЗВАННОЙ причиной: отправлено; не задан `RESEND_API_KEY`; Resend
ответил ошибкой (её текст рядом — чаще всего домен из `MAIL_FROM` не
подтверждён в Resend); не достучались до Resend; автор снял галочку
«прислать письмом»; у автора нет почты в аккаунте. Причину отдаёт сам
`mailer.send` полем `reason` — раньше все три внешних отказа сливались в
один `{ok:false}` и различались только по stdout. Сам адрес в журнал не
пишется — только id, название и исход.

## Комментарии к пазлам

Лента под страницей пазла (`/puzzle/:id`) и вкладка «Комментарии» в Admin.
Принятые решения (все — выбор пользователя, не умолчания):

- **Пишут только вошедшие.** Гость ленту видит, но вместо формы получает
  приглашение войти. Рейтинги, в отличие от этого, анонимные — там нечему
  быть злоупотреблением, а свободный текст от анонима это магнит для спама,
  на который нечем ответить: ни забанить толком, ни написать автору.
- **Постмодерация.** Комментарий виден сразу, лишнее сносит админ. При
  нынешней аудитории премодерация означала бы почти всегда пустую ленту и
  очередь, которую некому разбирать.
- **Уведомлений автору пазла пока нет.** Канал Auth для этого готов (см.
  `notify` в ответах approve/reject), добавить можно отдельной правкой.

Ключ — `image_file`, та же группировка, что у рейтингов: одна картинка —
один тред, общий для всех уровней сложности. Комментарии есть только у
БИБЛИОТЕЧНЫХ пазлов (`owner_user_id IS NULL`) — у чужой непроверенной
загрузки и своего черновика в комнате их нет вовсе, `/comments` отвечает
404. Автор денормализован в строку (`author_username`/`author_name`), как
`uploader_*` и `room_members`.

Удалить может автор своей реплики и админ — любую: право приходит claim'ом
`admin` в токене (см. `Auth/lib/tokens.js`), сервер отдаёт его клиенту полем
`canModerate`, и крестик появляется прямо на странице пазла, без похода в
админку. Удаление НАСТОЯЩЕЕ (`DELETE`), «мягкого» флага нет — зато текст
снесённого уходит в `adminLog` вместе с автором: иначе от комментария не
осталось бы следа, а именно он нужен, чтобы заметить, кто повторяется.

Ограничения: 1000 символов на комментарий, 20 комментариев в час на автора
(`MAX_COMMENT_LEN`/`MAX_COMMENTS_PER_HOUR`), сверх лимита — 429. В
SSR-снимок и в `sitemap.xml` комментарии НЕ попадают: пользовательский
текст на индексируемой странице — это способ занести спам прямо в выдачу,
лента рендерится только клиентом.

## GigaChat — короткие названия

Используется в двух местах: автогенерация названия при импорте с Pexels
(`gigachat.titleFromText`/`titleFromImage`) и кнопки «✨ по тексту»/«✨ по
фото» в библиотеке Admin (`/internal/puzzles/:id/title/suggest`, см.
`gigachat.js`). Разница между режимами принципиальная: «по тексту»
пересказывает существующее название, «по фото» смотрит **только на саму
фотографию** — ни старое название, ни категория в запрос не уходят. Иначе
модель пересказывает их вместо снимка, и режим теряет смысл: у фото,
импортированных с Pexels без `alt`, название вообще склеено из имени
категории (`«Библиотека 1»`, см. `Admin/assets/app.js`), так что название и
категория там — один и тот же текст. Ключ живёт **только в окружении сервера**: в браузер не
попадает, в образ не зашивается, в репозиторий не коммитится. Без
`GIGACHAT_AUTH_KEY` сервис работает как раньше, эндпоинт отвечает `503
gigachat_disabled`.

Домены Сбера подписаны корневым сертификатом Минцифры, которого нет в
alpine — без него TLS не поднимется (тот же приём, что у Trip).

### Настройка на сервере

Оба файла кладут рядом с `docker-compose.prod.yml` (то есть в `~/Puzzle/`),
в репозиторий они не попадают.

```bash
cd ~/Puzzle

# 1. Ключ — в .env рядом с compose (права 600), та же переменная,
# что ADMIN_INTERNAL_KEY.
# GIGACHAT_AUTH_KEY=ключ_из_Сбер_Студии

# 2. Корневой сертификат Минцифры.
curl -fsSL https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer \
  -o russian_trusted_root_ca.pem
chmod 644 russian_trusted_root_ca.pem

# 3. Убедиться, что файл текстовый (PEM), а не двоичный (DER):
head -1 russian_trusted_root_ca.pem   # ожидаем -----BEGIN CERTIFICATE-----

docker compose up -d
```

Имя файла должно совпадать с тем, что в `docker-compose.prod.yml`
(`russian_trusted_root_ca.pem`) — путь монтирования прописан там буквально.

**Ловушка**, в которую уже попадали: если запустить `docker compose up`
РАНЬШЕ, чем положить сам `.pem` на сервер, Docker молча создаёт на месте
bind-mount'а пустую ДИРЕКТОРИЮ вместо файла — и на хосте, и внутри
контейнера — без единой ошибки. Дальше `NODE_EXTRA_CA_CERTS` указывает на
директорию, Node её просто игнорирует, и TLS к Сберу падает с
`SELF_SIGNED_CERT_IN_CHAIN`, как будто сертификата нет вовсе. Проверка:

```bash
docker compose exec puzzle ls -la /app/certs/
# ожидаем -rw-r--r-- (файл), НЕ drwxr-xr-x (директория)
```

Если директория — `docker compose down`, `rm -rf russian_trusted_root_ca.pem`
на хосте, повторить шаг 2 выше, `docker compose up -d`.

Проверка, что всё село:

```bash
docker compose exec puzzle printenv NODE_EXTRA_CA_CERTS
docker compose exec puzzle node -e "fetch('https://gigachat.devices.sberbank.ru/api/v1/models').then(r=>console.log('TLS в порядке, ответ',r.status)).catch(e=>console.log('не вышло:',e.message))"
```

Ответ `401` — это успех: соединение установилось, а без токена и должно
быть «не авторизован». `fetch failed`/`SELF_SIGNED_CERT_IN_CHAIN` означает,
что сертификат не подхватился (см. ловушку выше).

Хватает одного корневого сертификата — промежуточный не нужен. Он
публичный, секретом не является; менять придётся, только когда Минцифры
выпустит новый — тогда достаточно заменить файл и перезапустить контейнер,
пересобирать образ не нужно.

## Миниатюры обложек

Обложки отдавались в исходном разрешении: карточка в сетке — слот 318×238
(`.puzzle-card-thumb`, `aspect-ratio:4/3` + `object-fit:cover`), а грузилось
в неё фото 1880×1253, то есть примерно в 35 раз больше пикселей, чем
показывается. Замеры на живом сайте: главная — 3.5 МБ за заход (2.8 МБ из
них картинки), `/category/cats` — 3.9 МБ на 21 обложку, отдельные файлы по
300–490 КБ. Вёрстку это не ломало (слот фиксированный, сдвига разметки нет),
ломало скорость — и через неё поведенческие, которые для Яндекса весят
больше, чем любая разметка.

Решение: сервис держит рядом с оригиналом две пережатые копии и отдаёт в
карточки их.

- **Два размера, 400 и 800.** 400 — карточка в сетке и обложка категории,
  800 — та же карточка на retina (через `srcset`), превью в модалках и
  картинка на `/puzzle/:id`. Белый список в `lib/thumbs.js`, не произвольное
  число из адреса: иначе любой желающий заставил бы сервис пережимать одну
  картинку под сколько угодно размеров.
- **Оригинал остаётся за столом.** Из него нарезаются детали
  (`createPieceEl`), миниатюра там дала бы мыло. Превью рядом со столом тоже
  берёт оригинал — он к этому моменту уже в кэше браузера под детали.
- **Адрес без расширения** — `/uploads/thumb/400/<uuid>`. На диске миниатюра
  бывает и `.webp` (vips в проде), и `.jpg` (sips на macOS при локальной
  разработке); формат браузеру сообщает `Content-Type`, он и так главнее
  расширения, а адрес от того, какой инструмент нашёлся на машине, не
  зависит и не меняется при переезде dev → прод.
- **Пережимает внешняя программа, не Node.** Декодировать JPEG стандартной
  библиотекой нечем, а npm-зависимость сломала бы главное свойство сервиса —
  зависимостей нет вовсе. Системный бинарник этого свойства не трогает: это
  зависимость образа (`apk add --no-cache vips-tools`, одна строка в
  Dockerfile), а не кода. Выбран vips, а не imagemagick — вчетверо меньше в
  образе и быстрее на ровно этой задаче. `lib/thumbs.js` ищет по PATH
  `vips` → `vipsthumbnail` → `magick` → `convert` → `sips`, так что
  локально на macOS ставить ничего не нужно.
- **Без vips сервис работает.** Нет инструмента, битый файл, нет места — по
  адресу миниатюры отдаётся ОРИГИНАЛ, с коротким `Cache-Control` вместо
  `immutable`. Страница выглядит как до правки, просто тяжёлой; сломанного
  `<img>` не бывает никогда. Этим же отличием в заголовке тест и определяет,
  какой путь отработал, не разбирая байты картинки.
- **Генерация ленивая + разовый прогрев.** Миниатюры заводятся при загрузке
  фото (оба входа — `POST /api/puzzles` и `POST /internal/puzzles`), а для
  уже лежащих ~480 обложек — на первый запрос. Отдельная миграция перед
  деплоем поэтому не нужна, но первое пережатие попадёт в ответ живому
  посетителю, причём залпом (Яндекс обходит категории подряд, по два десятка
  картинок на каждой). Поэтому сразу после деплоя:

      docker compose exec puzzle node scripts/backfill-thumbs.mjs

  Скрипт идемпотентен, базу не трогает вовсе — идёт по файлам в каталоге
  оригиналов. `--force` пережимает заново (нужно, если поменялись размеры
  или качество).
- **Лежат в томе.** `DATA_DIR/puzzle-thumbs/<размер>/<uuid>.<ext>`, рядом с
  `puzzle-photos`; том монтируется на `DATA_DIR` целиком, так что миниатюры
  переживают пересоздание контейнера. Отдельный каталог, а не подкаталог
  внутри `puzzle-photos` — тот отдаётся по `/uploads/` по basename с
  проверкой расширения, и подкаталог там пришлось бы отдельно исключать.
  Удаление пазла уносит и миниатюры.

Замер на настоящей обложке библиотеки — 1880×1253, 313 КБ JPEG:

| что отдаётся | размер | JPEG (sips, локально) | WebP (vips, прод) |
|---|---|---|---|
| оригинал (было) | 1880×1253 | 313 КБ | — |
| `thumbUrl`, обычный экран | 400×266 | 21 КБ | **7 КБ** |
| `previewUrl`, retina и телефон | 800×533 | 79 КБ | **22 КБ** |

То есть карточка в сетке становится легче в 45 раз на обычном экране и в 14
раз на retina. В пересчёте на страницы: главная грузила 13 обложек выше
сгиба на 2.8 МБ — станет около 90 КБ и 290 КБ соответственно;
`/category/cats` грузила 21 обложку на 3.9 МБ — станет около 150 КБ и 460 КБ.

Проверка в тестах не про байты, а про контракт: что по адресу миниатюры
всегда приходит рабочая картинка, что 400px заметно легче оригинала, что
непережимаемый файл отдаётся оригиналом с коротким кэшем и что размер не из
белого списка миниатюрой не отдаётся. Сравнение «миниатюра легче» на
синтетическом шуме врало бы (JPEG сжимает шум хуже PNG, уменьшенная копия
выходила БОЛЬШЕ оригинала) — поэтому фикстура градиентная, см.
`gradientPng` в `test/e2e-rooms.mjs`.

Чего эта правка НЕ исправила, хотя рядом: любой неизвестный путь (включая
`/uploads/thumb/<не тот размер>/…`) по-прежнему отдаёт главную страницу с
кодом 200, а не 404. Это отдельная задача, см. «Открытые вопросы».

## Дизайн

Подключено: вещество — бор (зелёное пламя, `--flame-tip:#7ddf3c`,
`--flame-base:#3f6212` в `assets/styles.css`), вписано в реестр
[`Design/services.md`](../Design/services.md). Повадка искр — своя,
`interlock` (добавлена в `Shared/brand.css` рядом с settle/motes/wind/
pulse/flicker, задокументирована в
[`Design/motion.md`](../Design/motion.md)): искра блуждает вбок, как
будто ищет своё место, затем «щёлкает» на позицию вспышкой и дальше
идёт ровно вверх без блужданий — та же вспышка (в цвет пламени) играет
и на самой детали пазла при снапе на стол, так что фон и обратная связь
сборки говорят одним цветом.

Не сделано: фавикон (нужна визуальная сверка рядом с остальными пятью —
шаг чек-листа, который не проходится вслепую).

## Открытые вопросы для будущих задач

- **Честный 404.** Сейчас любой неизвестный путь отдаёт главную страницу с
  кодом 200 — и `/nonexistent`, и `/puzzle/<несуществующий id>`, и
  `/category/<нет такой>`, и `/blog`, и `/yandex_<любые цифры>.html`. Для
  поиска это soft-404: жжётся краулинговый бюджет, а любая внешняя ссылка на
  произвольный путь заводит ещё одну страницу-копию главной.
- **`/table/:id` — дубль `/puzzle/:id`.** Одинаковые title/description/h1, и
  у каждого свой self-canonical. Нужен либо canonical с `/table/` на
  `/puzzle/`, либо `noindex` на стол.
- **Текст на страницах пазлов.** 477 страниц, уникального текста на каждой —
  заголовок и одно предложение (~90 символов из 2500: остальное шапка,
  футер и общий блок FAQ). Плюс разметка `FAQPage` дублируется на каждой
  странице сайта, хотя должна быть только на `/`.
- Пикер друзей через Auth API для приглашения в комнату (сейчас — только
  ссылка).
- Кик/удаление участников из комнаты, presence-курсоры (не только факт
  «кто подключён», но и где именно смотрит).
- Эндпоинт и формат приёма файлов от Admin.
- Публикация своих фото в общую библиотеку (сейчас свои фото приватны и
  доступны только автору в комнатах) — следующая задача, пока не начата.
